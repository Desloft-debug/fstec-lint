# Аутентификация: ГОСТ Р 58833-2020 как основание severity

**ГОСТ Р 58833-2020** «Защита информации. Идентификация и аутентификация.
Общие требования» (введён приказом Росстандарта от 10.04.2020 N 159-ст,
разработан ФСТЭК России; приказ ФСТЭК N 117 на него ссылается) даёт то,
чего в проекте не было: нормативное основание для severity правил об
аутентификации.

Раздел 7.2 связывает **вид** аутентификации с достигаемым **уровнем
доверия к её результатам** напрямую — без оценочных суждений:

| Вид аутентификации | Метод | Уровень доверия |
|---|---|---|
| простая (п. 3.46) | однофакторная односторонняя | **низкий** |
| усиленная (п. 3.59) | многофакторная односторонняя или взаимная | **средний** |
| строгая (п. 3.54) | многофакторная взаимная + криптографические протоколы | **высокий** |

Пункт 6.9 прямо называет доступ по паролю односторонней однофакторной
аутентификацией: «При односторонней однофакторной аутентификации по
паролю услуги доверенной третьей стороны не используются…». То есть
пароль — это простая аутентификация, а простая аутентификация по
разделу 7.2 даёт низкий уровень доверия. Дальше рассуждать не нужно.

## Осторожно: два разных «уровня доверия»

Их легко перепутать, и ошибка будет заметной.

| Где | Что означает | Значения |
|---|---|---|
| ГОСТ Р 58833-2020, разд. 7 | уверенность в результате идентификации и аутентификации | низкий / средний / высокий |
| Приказ ФСТЭК N 117, п. 72 | класс доверия к **средству защиты информации** | 4 / 5 / 6 (К1 / К2 / К3) |

Первое — про то, насколько можно верить, что субъект тот, за кого себя
выдаёт. Второе — про то, насколько можно верить самому СЗИ. В
`fstec_lint/auth.py` описан только первый; про второй там предупреждение.

## Какие правила на чём основаны

| Правило | Что проверяет | Пункт ГОСТ Р 58833-2020 |
|---|---|---|
| `S002` | `PasswordAuthentication yes` | 6.9 — доступ по паролю есть простая аутентификация; 7.2 — низкий уровень доверия |
| `S003` | `PermitEmptyPasswords yes` | 6.3 — проверка соответствия предъявленного идентификатора не выполняется |
| `P001` | `trust` / `md5` в `pg_hba.conf` | 3.46, 7.2 — простая аутентификация со слабым хранением |
| `P006` | `password_encryption` | 6.18 — метод хранения аутентификационной информации |
| `C004` | секрет в `environment` | 6.18 — устройства аутентификации не должны входить в состав объекта доступа |
| `D003` | секрет в `ARG` | 6.18 — то же |

Ссылки проверяются тестами: правило не может сослаться на пункт, которого
нет в `fstec_lint/auth.py`, а S002 и P001 обязаны называть уровень
доверия явно.

## Чего стандарт не даёт

Это стандарт общих требований, а не конфигураций. В нём нет ни длины
пароля, ни периодичности смены, ни перечня допустимых алгоритмов
хеширования. Конкретные значения приходят из других документов — так,
требование к паролю не менее 12 символов с буквами обоих регистров и
специальными символами задано **Методикой оценки Кзи** (утв. ФСТЭК
11.11.2025), приложение № 1, показатель `k21`.

Поэтому правила про SUPERUSER в PostgreSQL и про учётные записи с
паролями по умолчанию на этом стандарте построить нельзя — он не про то.
Их основание — `k21` и `k23` Методики Кзи и подмеры `УПД.3`
«Управление учётными записями» методического документа от 12.04.2026.
