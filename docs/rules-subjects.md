# Правило → предмет проверки

Таблица составлена по коду проверок в `fstec_lint/checks/`, а не по
заголовкам правил: важно, что проверка **фактически** детектирует.

Это карта технических признаков. Ссылки на приказ № 117, методический
документ от 12.04.2026 и приказ № 21 приведены отдельно в
[документации о нормативных связях](measures-117.md) и в каталоге
`fstec-lint --list-rules --format json`. Такие ссылки не подтверждают
ни применимость, ни выполнение меры.

Условия ниже относятся к конфигурации и поддерживаемым входам.
Отсутствие строки, файла или наблюдения не заменяет проверку действующих настроек.

## docker-compose.yml

| Правило | Предмет проверки | Условие срабатывания |
|---|---|---|
| C001 | Пользователь, от которого работает процесс в контейнере | нет `user:` либо `user` указывает на root / uid 0 |
| C002 | Отказ от изоляции контейнера целиком | `privileged: true` |
| C003 | Расширение привилегий контейнера через Linux capabilities | в `cap_add` есть SYS_ADMIN, NET_ADMIN, ALL, SYS_PTRACE или SYS_MODULE |
| C004 | Секрет, хранимый в конфигурации в открытом виде | имя переменной в `environment` похоже на секрет (PASSWORD, SECRET, TOKEN, API_KEY, PRIVATE_KEY, ACCESS_KEY) и значение непустое: либо литерал, либо подстановка с непустым значением по умолчанию (`${VAR:-changeme}`). Простая ссылка `$VAR` / `${VAR}` и имена на `_FILE`/`_FILENAME` исключены; значение с `$` в начале, не являющееся ссылкой (`$$ecret` — экранированный литерал), считается секретом |
| C005 | Сетевая доступность СУБД, кэша, поискового движка с любого интерфейса хоста | опубликован порт 5432, 3306, 6379, 27017, 9200, 1433 или 11211, адрес публикации не loopback (учитываются диапазоны портов и формы IPv6) |
| C006 | Воспроизводимость версии образа сервиса | `image` без тега, с `:latest` и без digest |
| C007 | Сетевая изоляция контейнера от хоста | `network_mode: host` |
| C018 | Изоляция PID | сервис явно задаёт `pid: host` |
| C019 | Изоляция IPC | сервис явно задаёт `ipc: host` |
| C020 | Делегирование доступа к API Docker | сервис явно включает `use_api_socket` |
| C008 | Доступ контейнера к управляющему сокету Docker | в `volumes` источник bind-монтирования называется `docker.sock` |
| C009 | Неизменяемость файловой системы контейнера | нет `read_only: true` |
| C010 | Возможность повышения привилегий внутри контейнера через setuid-бинарники | в `security_opt` нет `no-new-privileges` |
| C011 | Сетевая доступность управляющего API Docker | опубликован порт 2375 или 2376, адрес публикации не loopback |
| C012 | Ограничение потребления ресурсов хоста одним контейнером | нет ни `mem_limit`/`cpus`, ни `deploy.resources.limits` |
| C013 | Автоматическое обнаружение отказа сервиса | нет `healthcheck` либо он отключён (`disable`) |
| C014 | Режим отладки приложения в рабочей конфигурации | переменная окружения с именем, оканчивающимся на DEBUG, со значением 1/true/yes/on |
| C016 | Разделение сервисов по сетям | не менее двух сервисов используют сеть `default` явно или по умолчанию |
| C015 | Доступ контейнера к каталогам хоста | в `volumes` источник — `/`, `/etc`, `/proc`, `/sys`, `/var/run`, `/boot` или `/root` |

## Dockerfile

| Правило | Предмет проверки | Условие срабатывания |
|---|---|---|
| D001 | Пользователь, от которого стартует образ | в финальной стадии нет `USER` (с учётом наследования от локальной стадии) либо эффективный `USER` — root / uid 0 |
| D002 | Целостность файла, попадающего в образ из сети | `ADD` с HTTP(S)-источником без явно заданного SHA-256 |
| D003 | Попадание секрета в историю слоёв образа | имя `ARG` похоже на секрет (тот же набор, что в C004) |
| D004 | Воспроизводимость базового образа | `FROM` без тега или с `:latest` и без digest; ссылки на предыдущие стадии сборки и `scratch` не считаются |
| D005 | Выполнение кода, скачанного из сети, без проверки | в `RUN` (включая тело heredoc) вывод curl/wget передаётся конвейером в sh, bash или python |
| D006 | Автоматическое обнаружение отказа контейнера | в файле нет инструкции `HEALTHCHECK` |

## sshd_config

Проверяются глобальная секция (с умолчаниями демона) и каждый блок
`Match` — в блоке судится только явно заданное, унаследованное уже учтено
глобальной проверкой.

| Правило | Предмет проверки | Условие срабатывания |
|---|---|---|
| S001 | Возможность входа под root по SSH | `PermitRootLogin` = `yes`; `prohibit-password` и `without-password` не запрещают вход по ключу, но не вызывают правило |
| S002 | Способ аутентификации при SSH-доступе | `PasswordAuthentication` = `yes` (умолчание — `yes`) |
| S003 | Вход с пустым паролем | `PermitEmptyPasswords` = `yes` (умолчание — `no`) |
| S004 | Версия протокола SSH | `Protocol` содержит `1` (умолчание — `2`) |
| S005 | Проброс X11 через SSH-сессию | `X11Forwarding` = `yes` (умолчание — `no`) |
| S006 | Ограничение числа попыток аутентификации в сессии | `MaxAuthTries` больше 4 (умолчание — `6`) |

## Юниты systemd, секция `[Service]`

| Правило | Предмет проверки | Условие срабатывания |
|---|---|---|
| U001 | Пользователь, от которого работает системный сервис | `User` явно указывает на root (`root`, `ROOT`, `0`, `0:0`) либо не задан при выключенном `DynamicUser` |
| U002 | Повышение привилегий процессом сервиса через setuid-бинарники | `NoNewPrivileges` не истинен (`true`/`yes`/`on`/`1`) |
| U003 | Доступ сервиса на запись к системным каталогам хоста | `ProtectSystem` не `full`, `strict` или `yes` |
| U004 | Изоляция временных файлов сервиса | не указан включённый `PrivateTmp` или `disconnected`; при отсутствии параметра учитывается `DynamicUser` |
| U005 | Доступ сервиса к домашним каталогам пользователей | `ProtectHome` не `true`, `yes`, `on`, `1`, `read-only` или `tmpfs` |
| U006 | Ограничение записи службой в параметры ядра | В локальном результате `ProtectKernelTunables` явно выключен |
| U007 | Ограничение явной загрузки модулей ядра службой | В локальном результате `ProtectKernelModules` явно выключен |

## Что разбор не видит

Границы, за которыми отчёт «нарушений не найдено» означает лишь «в этом
файле не найдено». Ни одна из них не лечится проверкой — это свойства
самого статического разбора, и знать их нужно до того, как отчёт пойдёт
в документы.

- **Include не даёт полной модели работающего сервера.** SSH Include и три
  формы PostgreSQL раскрываются с ограничением выбранного дерева; внешние
  пути вызывают ошибку. Относительная база SSH — каталог основного файла.
  Подробности PostgreSQL: [postgresql-includes.md](postgresql-includes.md).
- **Образ в compose не разбирается.** C001 судит только по директиве
  `user:` в сервисе: если непривилегированный пользователь задан через
  `USER` в Dockerfile образа, находка всё равно будет. Обратное тоже
  верно — `USER root` в образе при отсутствии `user:` в compose видит
  D001, но не C001.
- **Переменные и профили compose не вычисляются.** `${VAR}` не
  подставляется (кроме литерального значения по умолчанию, см. C004), а
  сервисы под неактивным `profiles:` проверяются наравне с остальными.
- **Значение из `.env` не подставляется** в Compose; отдельные файлы `.env`
  проверяются правилами dotenv.
- **Формат `docker-compose` v1 не поддерживается.** Файл без единого
  ключа верхнего уровня современного compose (`services`, `version`,
  `volumes`, …) сообщается как ошибка разбора, а не проходит без предупреждения.
  Неизвестные корневые ключи также отклоняются: добавление `version` или
  `x-…` не делает корневой сервис современным Compose. Фрагменты только
  с известными ключами/расширениями остаются допустимыми. Это не полная
  валидация схемы Compose; проверяются структуры используемых полей.
  Для `privileged`, `read_only`, `healthcheck.disable` поддерживаются
  boolean и строки true/false, а также совместимые с compose-go y/yes/on
  и n/no/off без учёта регистра. Числа, строки 1/0, лишние пробелы и
  неизвестные значения дают ошибку; переменные по-прежнему не вычисляются.
  `healthcheck.test` допускает строку или список строк, но не mapping.
- **Обход дерева ограничен:** глубина каталогов от выбранного корня до 128,
  суммарно до 100 000 обнаруженных записей (файлов и каталогов). При
  превышении отчёт содержит ошибку неполного обхода, CLI не возвращает
  успешный код 0, ранее найденные нарушения сохраняются. Это не строгий
  лимит памяти/времени: `os.walk` сначала получает список одного каталога,
  файловая система может отвечать медленно. В CI нужен внешний timeout.
- **Dockerfile:** поддерживается начальная директива `# escape=\` или
  ``# escape=` ``. После пустой строки, обычного комментария или инструкции
  parser directives, как в Docker, уже не применяются. Неизвестный escape
  и повторная активная escape-директива дают ошибку. Dockerfile только
  читается, команды не исполняются. Пустые строки внутри продолжения
  пропускаются; два и более завершающих escape не продолжают инструкцию,
  согласно правилу BuildKit, а не shell-паритету.
- **`Include`/подключаемые файлы юнитов systemd** (`*.service.d/*.conf`)
  не раскрываются: drop-in переопределяет директиву основного юнита, а
  проверяется только сам `*.service`.

## Наблюдения

Побочный результат: несколько правил проверяют один и тот же предмет в
разных объектах. При переустановке кодов их, скорее всего, придётся
привязывать одинаково, а два случая заслуживают отдельного решения.

**Один предмет, разные объекты** — ожидаемо и, вероятно, одна подмера
на группу:

- пользователь процесса: C001 (сервис в compose), D001 (образ), U001 (юнит systemd);
- повышение привилегий через setuid: C010 (compose), U002 (systemd);
- изоляция файловой системы: C009 (compose), U003 и U004 (systemd);
- секрет в открытом виде: C004 (окружение сервиса), D003 (аргумент сборки).

**Дублирование в отчёте, требующее решения:**

- C013 и D006 — обнаружение отказа. Проект, где `HEALTHCHECK` не задан ни
  в Dockerfile, ни в compose, получит две находки об одной проблеме.
- C006 и D004 — закрепление версии образа. То же самое: незакреплённый
  базовый образ в Dockerfile и незакреплённый `image` в compose — это
  один недостаток воспроизводимости, показанный дважды.

В обоих случаях правила формально относятся к разным файлам и оба
срабатывания верны, но для читателя отчёта это одна проблема. Решать
после того, как станет понятна целевая гранулярность подмер: если новая
база разводит эти случаи по разным подмерам — оставляем как есть, если
сводит в одну — стоит подавлять парное срабатывание.

## Дополнительные типы конфигураций

Каталог включает 60 ID. Привязки ниже являются справочными ориентирами для проверки оператором, а не доказательством выполнения меры. Каталог не заменяет нормативную приёмку.

### Основания проверенных связей

Для ГИС использован [методический документ ФСТЭК от 12.04.2026, раздел IV](https://sudact.ru/law/metodicheskii-dokument-sostav-i-soderzhanie-meropriiatii-i/), детализирующий приказ № 117. Для ИСПДн использовано приложение к [приказу № 21 в редакции от 14.05.2020](https://www.sli.komi.com/files/info_bezop/prikaz_fstek_pers_dan_is.pdf); УПД.1 и АВЗ.1 включены в базовые наборы всех четырёх уровней. Применимость определяется типом системы и адаптацией мер оператором.

| Правила | Связь | Основание и предел проверки |
|---|---|---|
| A003 | УПД.3 методического документа; УПД.1 приказа № 21 | Блокирование относится к жизненному циклу учётной записи; INACTIVE касается только новых записей после истечения пароля. |
| M001 | ЗЭП.3; АВЗ.1 | Вредоносные вложения относятся к антивирусной защите; наличие фильтра не доказывает его эффективность. |
| C017, R001 | РСБ.4 | Мера охватывает сбор и хранение событий, централизованный сбор указан среди усилений; внешние сборщики не проверяются. |
| N001 | ЗВТ.1 | Мера охватывает защиту пользовательских данных при сетевом взаимодействии; проверяется лишь конфигурация TLS. |
| N002 | ЗВТ.2 | Неожиданный список файлов может раскрывать объекты доступа; проверка не устанавливает наличие чувствительных данных и общую модель доступа. |
| N003 | ЗВТ.4 | Мера охватывает регистрацию событий веб-приложений; access_log не доказывает полноту событий. |
| N004 | ЗОО.5; УПД.3 приказа № 21 | ЗОО.5 прямо предусматривает ограничение запросов и соединений; УПД.3 охватывает управление информационными потоками, включая контроль соединений. Ограничение запросов — частный индикатор, а не доказательство реализации меры; внешние ограничения не проверяются. |
