# Самооценка по ГОСТ Р 56939-2024

**ГОСТ Р 56939-2024** «Защита информации. Разработка безопасного
программного обеспечения. Общие требования» (введён приказом
Росстандарта от 24.10.2024; приказ ФСТЭК N 117 ссылается на него, а
пункт 34 м) Требований делает разработку безопасного ПО отдельным
мероприятием) описывает 25 процессов разработчика.

Стандарт про процессы разработчика, а не про проверяемые конфигурации.
Поэтому он не даёт новых правил линтеру — он задаёт мерку **самому
проекту**. Ниже честная самооценка: что реализовано, что частично, чего
нет. Пункт 4.11 называет артефактом «любую информацию (документы,
отчёты, файлы, журналы, результаты работы инструментов, процессов),
сохранённую в любом виде».

Оценка сделана разработчиком, внешний аудит не проводился.

## Реализовано

| Процесс | Артефакты |
|---|---|
| 5.4 Управление конфигурацией ПО | git, семантическое версионирование, `CHANGELOG.md`, `constraints.txt` с версиями инструментов |
| 5.8 Правила кодирования | `ruff` и `ruff format` с конфигурацией в `pyproject.toml`, проверка в CI на каждый push и PR |
| 5.10 Статический анализ кода | `ruff` (E, F, W, UP, I, B) и `mypy` в строгом режиме (`disallow_untyped_defs`, `strict_equality`), оба блокируют сборку |
| 5.15 Безопасность используемых секретов | секретов в репозитории нет; п. 5.15.2.3 требует проверять конфигурационные файлы на их включение — это и есть правила C004 и D003 самого инструмента |
| 5.18 Функциональное тестирование | 272 теста на Python 3.10–3.12, порог покрытия 90% (фактическое 95%), регрессия на каждый закрытый дефект, самосканирование двух стендов с проверкой кодов возврата |

Пункт 4.13 требует от среды разработки контроля версий, непрерывной
интеграции и управления задачами: git, GitHub Actions и GitHub Issues.

## Что делать дальше, по приоритету

1. **5.7 Моделирование угроз.** Инструмент читает чужие файлы: битый YAML, огромные файлы, вложенные якоря, символьные ссылки. Часть защит уже есть (лимит размера compose, обработка ошибок разбора по файлам), но модели угроз, которая объясняет их полноту, нет.
2. **5.11 Фаззинг парсеров.** Пять парсеров на недоверенном вводе. Дефекты 1.10 и 1.1 из истории проекта фаззер нашёл бы сразу.
3. **5.14 Подпись коммитов и 5.21 контрольные суммы поставки.** Без этого целостность кода и дистрибутива ничем не подтверждена.
4. **Регламенты.** Их отсутствие — главная причина, по которой большинство строк выше стоят как «частично»: практика есть, документа нет. Пункт 4.12 разрешает объединить их в одно руководство по разработке безопасного ПО.

## Чего этот стандарт не даёт линтеру

Правил проверки конфигураций из него не выводится: он описывает
процессы, а не предикаты. Надежда получить из него правила про
multistage-сборку и хеш-суммы пакетов не оправдалась — таких требований
в нём нет. Что он действительно дал существующим правилам:

| Правило | Пункт |
|---|---|
| `C004`, `D003` | 5.15.2.3 — проверять конфигурационные файлы на включение секретов; статический анализ прямо допускается |
| `C006`, `D004` | 5.16.3.2 — перечень зависимостей с версиями и источником; 5.13.2.6 — повторяемость сборки |
| `D002` | 5.17.2.1 — контроль цепочки поставок |
| инструмент целиком | 5.24.2.3 — проверки настроек конфигураций ПО при эксплуатации на регулярной основе |
