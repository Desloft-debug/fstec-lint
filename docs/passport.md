# Паспорт уязвимости по ГОСТ Р 56545-2015

`fstec-lint --format passport` выводит находки в форме паспорта
уязвимости по **ГОСТ Р 56545-2015** «Защита информации. Уязвимости
информационных систем. Правила описания уязвимостей» (введён приказом
Росстандарта от 19.08.2015 N 1180-ст, переиздание октябрь 2018 г.),
приложение А.

Приказ ФСТЭК N 117 ссылается на этот стандарт, а пункт 20 и) Методики
оценки Кзи называет исходными данными «результаты работы
инструментальных средств оценки (анализа) защищённости». Паспорт — та
форма, в которой их ждут: отчёт прикладывается к материалам оценки как
есть, а не переписывается руками.

```bash
fstec-lint . --format passport --output passports.txt
```

## Состав элементов

Стандарт делит элементы на три группы. Ниже — что подставляет
инструмент.

### Обязательные для идентификации (п. 5.1.2)

| Элемент | Источник |
|---|---|
| Идентификатор уязвимости | `FLINT-<год>-<номер>` по формату п. 5.2.3: код базы, год, порядковый номер через `-` |
| Наименование уязвимости | заголовок правила и адрес находки |
| Класс уязвимости | `уязвимость конфигурации` |
| Наименование ПО и его версия | тип разбираемого файла; версия не определяется |

### Обязательные для работ по анализу (п. 5.1.3)

| Элемент | Источник |
|---|---|
| Идентификатор типа недостатка | `CWE-…` из поля `cwe` правила |
| Тип недостатка | `weakness_type` правила |
| Место возникновения (проявления) уязвимости | путь к файлу и строка |
| Способ (правило) обнаружения уязвимости | идентификатор правила и его предикат |
| Возможные меры по устранению уязвимости | `remediation` правила |

Пункт 5.2.16 требует «формализованное правило определения уязвимости»
и приводит в пример OVAL. У статического линтера такое правило есть по
построению: это сам идентификатор проверки и предикат, который она
вычисляет, — они и подставляются.

### Степень опасности (п. 5.2.18)

Стандарт задаёт ровно четыре значения, и шкала инструмента совпадает с
ними один в один:

| severity | ГОСТ Р 56545-2015 |
|---|---|
| `critical` | критический уровень опасности |
| `high` | высокий уровень опасности |
| `medium` | средний уровень опасности |
| `low` | низкий уровень опасности |

## Чего инструмент не заполняет

Элементы, которые статический анализ конфигураций определить не может,
помечаются явно — «не определяется статическим анализом конфигурации».
Пустое поле честнее правдоподобного:

- **версия ПО** — в конфигурационном файле её нет;
- **наименование ОС и тип аппаратной платформы** — то же;
- **язык программирования ПО** — неприменимо к конфигурации;
- **идентификаторы других систем описаний** (CVE, BDU) — находка не
  является известной уязвимостью компонента;
- **критерии опасности** (базовый вектор CVSS, п. 5.2.17) — шесть
  критериев требуют оценки в конкретной системе, а не в отрыве от неё;
- **служба (порт)** — заполняется только для правил C005 и C011, где
  порт есть в самой находке.

## Что требует проверки перед формальным применением

Два элемента проставлены по общедоступным источникам, а не по тексту
стандарта, и перед подачей материалов их стоит сверить.

**Класс уязвимости.** Пункт 5.2.6 требует определять класс «в
соответствии с ГОСТ Р 56546». Текста ГОСТ Р 56546 «Защита информации.
Уязвимости информационных систем. Классификация уязвимостей
информационных систем» в проекте нет, поэтому класс проставлен как
«уязвимость конфигурации» по смыслу разбираемых объектов. Точную
формулировку нужно взять из стандарта.

**Идентификаторы типа недостатка.** Пункт 5.2.11 прямо разрешает брать
идентификатор из общедоступных источников, и использован CWE
(cwe.mitre.org): 20 различных идентификаторов на 40 правил. Сопоставление
сделано по смыслу проверки и перед формальным применением подлежит
сверке с каталогом CWE. Наименования типов недостатка в поле
`weakness_type` — перевод названий CWE, а не цитата ГОСТ Р 56546.
