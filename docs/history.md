# История проверок разработки

У fstec-lint уже есть baseline: он скрывает принятые находки из текущего отчёта. История решает другую задачу: связывает коммиты, фактически выполненные проверки и результаты разных инструментов. Она включается явно; сеть и отдельная СУБД не нужны. Для истории требуется SQLite 3.31+ из поставки Python.

## Запуск

```sh
fstec-lint ./repo --select D004 --history-db ./checks.sqlite3 \
  --project demo --revision <commit> --run-key <ci-job-id>
fstec-lint history import-junit ./checks.sqlite3 unit-tests.xml \
  --project demo --revision <commit> --runner-version pytest-9 --profile unit
fstec-lint history list ./checks.sqlite3 --project demo
fstec-lint history diff ./checks.sqlite3 1 2
```

`--project` и `--revision` – метки, их подаёт CI. CLI не удостоверяет Git-коммит самостоятельно. Идентификатор прогона печатается в stderr, формат обычного отчёта и порог не меняются. Код 2 при ошибке записи не означает, что анализ «чистый». Если `--run-key` передан снова для той же метки коммита и инструмента, идентичный набор результатов не дублируется, а другой результат с тем же ключом отклоняется. Без ключа каждый запуск отдельный.

## Модель данных

```text
projects 1 ── N revisions 1 ── N runs 1 ── N observations 1 ── N findings
definitions (tool, code) 1 ────────────────────── N observations
```

- `projects` – постоянный идентификатор репозитория. `revisions` – метка конкретного состояния, уникальная внутри проекта.
- `runs` – инструмент, версия, отпечаток профиля, время и количество ошибок. На один коммит возможны несколько инструментов и повторных запусков.
- `definitions` – справочник кодов проверок; `observations` связывает его с прогонами и областью проверки. Составные внешние ключи запрещают связать наблюдение с определением другого инструмента. Составное ограничение уникальности не даёт записать один результат по одному коду и области дважды.
- `findings` – отдельные нарушения в рамках наблюдения. Одна проверка одного входного файла может вернуть несколько находок. Вместо текста правила и фрагментов файла хранится SHA-256 стабильного идентификатора (код, путь от корня проверки, позиция по смыслу) и номер строки для навигации. Сдвиг строки не создаёт новую находку. Это тот же принцип идентификации, что в baseline/SARIF, но строковое представление ключа и длина хеша здесь не являются форматом обмена.

## Как читать сравнение

- Сравниваются два разных прогона одного проекта, инструмента, версии и профиля. Используйте одинаковую границу сканирования (корень репозитория или тот же одиночный файл).
- `resolved` означает, что прежняя находка исчезла при сопоставимой выполненной проверке; `new` – обратный переход. Это результат проверки файла, не аттестация.
- Если файл не проверен, не разбирается или прогон частичный, нет основания засчитать исправление. Сравнение возвращает `unknown` для обнаруженных различий и не даёт считать пустой diff доказательством полного покрытия. Число наблюдений и ошибок видно в `history list`. Подавленные baseline и комментариями находки остаются наблюдениями до фильтрации; иначе изменение подавления выглядело бы как исправление.
- JUnit читается отдельно: `pass`, `fail`, `skip`, `unavailable`. В агрегированном списке одного коммита можно видеть оба инструмента. При наличии итоговых счётчиков они сверяются с отдельными тестами. Содержимое сообщений об ошибках и stdout тестов не сохраняется.

## Проверка работы истории

Из корня репозитория с установленным пакетом запустите:

```sh
python examples/history-demo.py ./demo-history
```

Сценарий создаёт новый каталог с тестовыми конфигурациями, SQLite-базой и
результатами команд. Он проверяет три исхода:

| Сценарий | Результат |
| --- | --- |
| В ревизии B устранена настройка, на которую сработало D004 в ревизии A | Сравнение возвращает `resolved` |
| Входной файл следующего прогона не разобран | Сравнение возвращает `unknown`, а не `resolved` |
| Для той же ревизии импортирован JUnit | В списке прогонов видны оба инструмента и их отдельные результаты |

Для выборок по обычной SQLite используйте [history_queries.sql](history_queries.sql).
Тестовые конфигурации не выполняются, Docker не запускается.

## Границы хранения

Сохраняются относительные пути, названия JUnit тестов, статусы и отпечатки. Не передавайте секреты в имена/пути/метки: эти поля остаются видимыми. Сам файл SQLite храните в приватном каталоге вне дерева сканирования и не добавляйте в Git. Новая база создаётся с правами доступа владельца на POSIX; на Windows действуют ACL каталога. Служебные файлы SQLite и внешние отчёты защищаются отдельно. SQL использует параметры. Импорт JUnit ограничен размером, не разрешает DTD и не выполняет из файла команды. База не принимает отчёты по сети и не заменяет разграничение проектов. Используйте формат `.fsth`, если требуется шифрование файла.

Для сканирований этой сборки профиль также включает отпечаток исходников анализатора, строгость и порядок явно заданных Compose-слоёв. Базы более ранних сборок по-прежнему открываются; сравнение нового прогона с прежним несовместимым профилем не превращает смену реализации проверки в исправление проекта.

## Зашифрованная локальная история

Для хранения истории в зашифрованном виде установите дополнительную зависимость.
Нужен Python 3.11 или новее со сборкой SQLite, поддерживающей `serialize` и
`deserialize`. Обычные базы SQLite по-прежнему работают без этой зависимости.

**PowerShell** (в активированном окружении, из корня репозитория):

```powershell
python -m pip install -e ".[history-encryption]"
fstec-lint history init-key "$HOME\fstec-history.key"
$env:FSTEC_LINT_HISTORY_KEY_FILE = "$HOME\fstec-history.key"
fstec-lint .\repo --history-db .\history.fsth --project demo --revision rev-a
fstec-lint history list .\history.fsth --project demo
```

**Linux** (из активированного окружения):

```sh
python -m pip install -e '.[history-encryption]'
fstec-lint history init-key "$HOME/fstec-history.key"
export FSTEC_LINT_HISTORY_KEY_FILE="$HOME/fstec-history.key"
fstec-lint ./repo --history-db ./history.fsth --project demo --revision rev-a
fstec-lint history list ./history.fsth --project demo
```

`init-key` создаёт двоичный случайный ключ, не выводит его и не перезаписывает
существующий файл. На POSIX доступ к ключу разрешён только владельцу; на Windows
разместите ключ в приватном каталоге с ограниченными ACL. Храните ключ вне
репозитория, отдельно от файла истории и резервных копий. Без этого ключа
открыть историю нельзя. Для разных баз используйте разные ключи.

Для перехода с обычной SQLite при установленных зависимости и переменной
окружения выполните:

```sh
fstec-lint history encrypt old.sqlite3 history.fsth
fstec-lint history list history.fsth --project demo
```

Исходная база не заменяется и остаётся незашифрованной. Назначение должно быть
новым. Проверьте зашифрованную копию и защитите исходник и его резервные копии отдельно.
Для обычной SQLite уберите переменную (`Remove-Item Env:FSTEC_LINT_HISTORY_KEY_FILE`
в PowerShell, `unset FSTEC_LINT_HISTORY_KEY_FILE` в Bash). Для `.fsth` ключ
обязателен: при его отсутствии или неверном значении команда завершается с кодом 2.

На диске лежит снимок SQLite, зашифрованный [AES-256-GCM][aesgcm]. Подлинность
снимка проверяется до передачи данных SQLite. База и её временные данные
обрабатываются в памяти, промежуточный файл записи содержит только шифртекст.
Лимит снимка 64 МиБ; снимок целиком читается или записывается при операции.
Параллельная запись в один файл не поддерживается: при конфликте повторите
операцию. После аварийной остановки может остаться соседний файл `.lock`;
убирайте его только после проверки, что писателей больше нет. Используйте
приватный локальный каталог, не сетевой общий ресурс.

Защита не распространяется на отчёты, память работающего процесса, дампы и файл
подкачки. Она не обнаруживает удаление, подмену более старым подлинным снимком
или изменение тем, кто получил ключ. Это не централизованный журнал аудита.

[aesgcm]: https://cryptography.io/en/latest/hazmat/primitives/aead/
