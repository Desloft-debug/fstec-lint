# fstec-lint

[![CI](https://github.com/Desloft-debug/fstec-lint/actions/workflows/ci.yml/badge.svg)](https://github.com/Desloft-debug/fstec-lint/actions/workflows/ci.yml)
[![License: MIT](https://img.shields.io/badge/license-MIT-blue.svg)](LICENSE)

Линтер конфигураций для подготовки информационных систем к аттестации.
Проверяет `docker-compose.yml`, `Dockerfile`, `postgresql.conf`,
`pg_hba.conf`, `sshd_config`, юниты systemd, `nginx.conf`, `login.defs`,
`pwquality.conf`, `/etc/default/useradd`, `rsyslog.conf` и `main.cf`
почтового сервера Postfix. Правил 53, у каждого есть
ссылка на пункт приказа ФСТЭК России N 117, подмеру методического
документа от 12.04.2026 и меру приказа N 21.

```
[CRIT] C011 Незащищённый Docker Engine API опубликован наружу
       файл: docker-compose.yml:26
       мера: п. 63 з) — Защита программных интерфейсов взаимодействия приложений
       подмера: ЗПИ.2 — Управление доступом пользователей и приложений
       ПДн:  ЗСВ.1 — Идентификация и аутентификация в виртуальной инфраструктуре
       фикс: Не публикуйте сокет Docker наружу; используйте TLS (--tlsverify).
```

Trivy, Checkov, Lynis и Docker Bench находят похожие ошибки, но ссылаются
на CIS Benchmarks и NIST. Для материалов аттестации нужны пункты приказов
ФСТЭК, и обычно их подбирают вручную. fstec-lint делает это сразу.

Ссылки на документы проверяются тестами: правило не может указать
несуществующий пункт или название, которое расходится с текстом приказа.

> Инструмент не заменяет аттестацию и не является сертифицированным
> средством защиты информации. Привязка к пунктам приказов справочная,
> перед использованием её стоит сверить с действующей редакцией
> документов, актом классификации и моделью угроз.

## Установка

```bash
pip install "fstec-lint @ git+https://github.com/Desloft-debug/fstec-lint.git@v1.0.1"
```

Зависимость одна — PyYAML. Нужен Python 3.10 или новее.

## Использование

```bash
fstec-lint путь/к/проекту
fstec-lint . --format html --output report.html
fstec-lint . --format docx --output report.docx      # отчёт по ГОСТ 7.32-2017
fstec-lint . --format passport --output passports.txt
fstec-lint . --format sarif --output report.sarif    # GitHub Code Scanning
fstec-lint . --format json --output report.json
fstec-lint . --fail-on critical                      # порог для кода выхода
fstec-lint . --uz 3                                  # базовый набор мер для УЗ3
fstec-lint --list-rules                              # каталог правил
```

Файлы ищутся рекурсивно. Каталоги `.git`, `node_modules`, `vendor`,
`.venv`, `site-packages`, `__pycache__`, `.terraform` и кеши линтеров
пропускаются всегда, остальное можно исключить через `--exclude`
(glob, флаг повторяется).

### Отчёт для материалов аттестации

`--format docx` формирует отчёт о результатах контроля конфигураций в
формате Word. Оформление по ГОСТ 7.32-2017: поля 30/15/20/20 мм, Times New
Roman 14 пт, полуторный интервал, абзацный отступ 1,25 см, нумерация
страниц внизу по центру, титульный лист без номера.

Структура отчёта:

- титульный лист и содержание;
- введение: цель контроля и нормативная база;
- объект и методика контроля: проверенные файлы, число применённых правил;
- результаты: сводка по степени опасности, по пунктам приказа N 117 и
  перечень находок;
- рекомендации по устранению;
- заключение;
- приложение А — паспорта уязвимостей по ГОСТ Р 56545-2015, по одному на
  находку.

Содержание собирается полем Word и обновляется при открытии файла. Если
нарушений нет, приложение не формируется, а в заключении это указано.
Для `docx` параметр `--output` обязателен.

### Паспорта уязвимостей

`--format passport` выводит находки в форме паспорта по ГОСТ Р 56545-2015
(приложение А). Заполняются элементы, обязательные по пп. 5.1.2 и 5.1.3,
в том числе тип недостатка (CWE) и правило обнаружения. Класс уязвимости,
тип недостатка и место возникновения указываются по ГОСТ Р 56546. Что
по конфигурации определить нельзя (версия ПО, платформа, вектор CVSS),
помечено «не определяется». Подробнее в [`docs/passport.md`](docs/passport.md).

### Отключение правил

Комментарий в проверяемом файле действует на свою и следующую строку:

```yaml
services:
  db:  # fstec-lint: ignore C001, C009   ← весь сервис
    image: postgres:16.4
    # fstec-lint: ignore C005            ← только эта директива
    ports:
      - "5432:5432"
```

Поддерживаются glob (`C0*`) и форма без списка — `# fstec-lint: ignore`.
Работает во всех форматах. Число подавленных находок печатается в stderr.

Для всего прогона есть `--ignore` и `--select` (id или glob, через
запятую). Шаблон, который не подошёл ни к одному правилу, считается
ошибкой вызова.

### Baseline

Чтобы подключить линтер к существующему проекту и не получить красный CI
в первый же день, текущие находки можно записать в baseline:

```bash
fstec-lint . --write-baseline .fstec-lint-baseline.json   # один раз
fstec-lint . --baseline .fstec-lint-baseline.json         # в CI
```

После этого сборка падает только на новых находках. Находка
идентифицируется по правилу, файлу и месту (`service:db`,
`sshd_config: PermitRootLogin`); номер строки и текст описания в
отпечаток не входят, поэтому правки выше по файлу baseline не ломают.
Файл отсортирован, его удобно смотреть в диффе.

### Коды выхода

| Код | Значение |
|-----|----------|
| `0` | находок выше порога `--fail-on` нет |
| `1` | есть находки уровня `--fail-on` или выше (по умолчанию `high`) |
| `2` | ошибка вызова: неверный путь, некуда записать отчёт, повреждён baseline, опечатка в `--select`/`--ignore` |
| `3` | находок выше порога нет, но часть файлов не удалось разобрать |

Если есть и находки, и неразобранные файлы, возвращается `1`. Файл,
который не удалось разобрать, пропускается с сообщением в stderr, скан
продолжается.

Пути в отчётах записываются относительно текущего каталога, поэтому
отчёты с рабочей машины и из CI совпадают. Запускать лучше из корня
проекта.

## Нормативная база

Состояние на 03.09.2026.

**Приказ ФСТЭК России от 11.04.2025 N 117** (зарегистрирован Минюстом
16.06.2025, N 82619) действует с 1 марта 2026 года и заменил приказ N 17.
Кодов мер вида `ЗСВ.2` в нём нет. Требования задают два перечня:

- п. 34 — 22 мероприятия по защите информации (контроль конфигураций,
  управление уязвимостями, привилегированный доступ и др.);
- п. 63 — 17 базовых мер. Среди них отдельно выделены защита контейнерных
  сред и их оркестрации (п. 63 д)) и защита программных интерфейсов
  (п. 63 з)).

**Методический документ ФСТЭК России от 12.04.2026** детализирует приказ:
19 мероприятий (раздел III) и 95 подмер в 17 группах (раздел IV). Каждое
правило привязано к подмере (например, `ЗКО.5`) и мероприятию (`ПД`).
Термины для группы ЗКО взяты из ГОСТ Р 70860-2023, на п. 3.10 которого
ссылается приказ.

**Приказ ФСТЭК России от 18.02.2013 N 21** действует для ИСПДн. Код меры
хранится в поле `pdn_measure`. Флаг `--uz` оставляет правила из базового
набора нужного уровня защищённости (для УЗ3 — 41 из 53). По умолчанию
проверяются все правила, так как пп. 9 и 10 приказа допускают адаптацию
набора. Проект замены приказа опубликован, но на дату выше не
зарегистрирован.

**ГОСТ Р 58833-2020** определяет, какой уровень доверия даёт вид
аутентификации. На нём основана степень опасности правил S002 и P001:
пароль — простая аутентификация — низкий уровень доверия.

### Ограничения

Инструмент поддерживает два мероприятия оператора: контроль конфигураций
(п. 34 б)) и контроль уровня защищённости (п. 34 ф)).

- Из 17 базовых мер п. 63 затрагиваются 10. Антивирусная защита,
  обнаружение вторжений, защита конечных устройств требуют данных о
  работающей системе.
- Для показателя Кзи инструмент даёт исходные данные по 10 частным
  показателям из 16 (`k21`–`k24`, `k31`–`k34`, `k41`, `k42`), их
  суммарный вес 0,7375. Сам показатель не рассчитывается:
  например, для `k21` видна парольная политика, но не пароли конкретных
  учётных записей. Разбор — в [`docs/kzi.md`](docs/kzi.md).
- Для уровня зрелости — материал в 10 направлениях из 21 по видам
  требований «Инструменты» и «Контроль». Структура методики выписана по
  вторичным источникам и ещё не сверена с текстом ФСТЭК.
- Директивы `include` в `postgresql.conf` пока не раскрываются.
  `Include` в `sshd_config` раскрывается в пределах проверяемого
  каталога: относительные пути и пути под `/etc/ssh` берутся от каталога
  с `sshd_config`, прочие абсолютные пути не читаются.

## Проверка на эталонных наборах

Качество правил измерено на чужой разметке: тестовых примерах сканера
KICS (Docker Compose, Dockerfile) и сценариях ComplianceAsCode для sshd,
где эталоном служит действующая конфигурация по `sshd -T`.

| Набор | TP | FP | FN | Точность | Полнота |
|---|---|---|---|---|---|
| KICS, 15 запросов, 82 примера | 46 | 4 | 1 | 92% | 98% |
| ComplianceAsCode, sshd, 70 сценариев | 23 | 4 | 0 | 85% | 100% |
| ComplianceAsCode, login.defs, pwquality, useradd, rsyslog, 32 сценария | 19 | 0 | 0 | 100% | 100% |

Единственный пропуск по KICS — ошибка разметки: анонимный том
`- /var/lib/backup/data` не монтирует каталог хоста. Лишние срабатывания
оставлены сознательно: инструмент рассчитан на дополнительную проверку,
и пропуск обходится дороже лишнего замечания. Сверка нашла дефекты в
правилах Compose, пробел в разборе `sshd_config` (не читались файлы
из `Include`), неверный порядок чтения `login.defs` и непрочитанный
каталог `pwquality.conf.d`, всё исправлено. Методика, разбор каждого расхождения и
команда для воспроизведения — в [`benchmarks/README.md`](benchmarks/README.md).

## GitHub Actions

```yaml
name: fstec-lint
on: [push, pull_request]

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: Desloft-debug/fstec-lint@v1.0.1
        with:
          path: .
          format: html
          output: fstec-lint-report.html
          fail-on: high
```

Отчёт сохраняется как артефакт, джоба падает на находках `high` и
`critical`.

## Устройство

```
fstec_lint/
├── parsers/      # разбор файлов с номерами строк
├── checks/       # проверки: разобранный файл → находки
├── rules/*.yaml  # метаданные правил: severity, меры, рекомендации
├── engine.py     # поиск файлов, запуск проверок
├── reporters/    # text, json, html, sarif, passport, docx
└── cli.py
```

Правило состоит из записи в YAML и функции в `checks/*.py` с тем же `id`.
Проверка возвращает `(location, detail, line)`: `location` используется
для baseline, `line` — для отчётов. Новый тип файла добавляется парсером,
реестром проверок, YAML с правилами и строкой в `engine.scan`.

## English

`fstec-lint` checks Docker Compose, Dockerfile, PostgreSQL, sshd_config
systemd units, nginx, login.defs, pwquality.conf, /etc/default/useradd, rsyslog.conf and Postfix main.cf, and maps each of its 53 rules to a clause of FSTEC
Order No. 117 (in force since 2026-03-01), a submeasure of the FSTEC
guidance of 2026-04-12, and a measure of Order No. 21 for personal data.
The mapping is checked by tests against the text of the documents.

Output formats: text, JSON, HTML, SARIF, vulnerability passports
(GOST R 56545-2015) and a DOCX report formatted per GOST 7.32-2017.

```bash
pip install "fstec-lint @ git+https://github.com/Desloft-debug/fstec-lint.git@v1.0.1"
fstec-lint . --format html --output report.html
fstec-lint . --format docx --output report.docx
fstec-lint . --write-baseline .fstec-lint-baseline.json
fstec-lint . --baseline .fstec-lint-baseline.json
```

Exit codes: `0` clean, `1` findings at or above `--fail-on` (default
`high`), `2` usage error, `3` some files could not be parsed.

This is not a certified security product and does not replace
certification. Verify the mappings against the current edition of the
orders before relying on them.
